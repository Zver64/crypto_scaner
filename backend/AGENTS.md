# Backend

## Architecture

Composition happens only in `cmd/crypto-scanner/app.go`: it builds every dependency, the HTTP handler, and the list of background services that `lifecycle.go` runs (HTTP first, then the services; the first to stop stops the rest). Add a new background service to that list instead of starting goroutines elsewhere.

Packages and dependency direction (domain never imports adapters):

- Domain: `market` (instruments, candles, intervals, `NormalizeSymbol`), `market/kline` and `market/trade` (exchange-neutral live feeds), `market/live` (demand-driven live candle subscriptions), `market/marketsync` (REST history sync and scheduler; `ObservableStore` reports committed candle changes and `ObservableRunner` the end of each synchronization round), `indicator` (registry of self-describing indicator modules plus `Registry.CalculateCandles`), `chart` (closed chart ranges and `LiveSession`, which merges live candles with history), `closedindicator` (background indicators on closed candles), `analysis` (criteria pipeline), `markettable` (backend-defined market tables), `scannerindicator` (administrator-configured indicators), `strategy` (administrator strategies over those indicators and their Telegram alerts), `users` (administrator user management), `favorites`, `alerts`, `marketcap`, `auth`.
- Adapters: `indicator/talib` (every TA-Lib function through one generic adapter), `exchange/binance` (REST client and one generic WebSocket `streamPool` for kline and trade streams), `coingecko`, `storage/postgres` (one `Store`, split into `store_*.go` by aggregate), `httpapi` (transport only), `telegrambot`, `auth/telegram` (init-data verification, no `net/http`).
- Authentication: `auth.Sessions` exchanges Telegram init data (at most `TELEGRAM_INIT_DATA_MAX_AGE` old, checked by `auth/telegram`) for an opaque random token through `POST /api/v1/auth/session`. Only the token's SHA-256 is stored in `app.sessions`, which cascades from `app.users`, so deleting a user revokes their sessions. Every other operation and the live candle WebSocket's `authenticate` message use the token (`Authorization: Bearer`); it expires after `SESSION_IDLE_TTL` without use and after `SESSION_ABSOLUTE_TTL`, and the WebSocket rechecks it every minute. Never accept init data elsewhere.
- Shared helpers: `platform/backoff` (retry delays, `Sleep`), `platform/numeric` (`Finite`, `ParseFinite`), `platform/logging`, `platform/config`.

Product constraints:

- Indicators are configured by the administrator, not in code. `scannerindicator` keeps the rows of `app.scanner_indicators` (TA-Lib type, canonical parameters, interval, `show_in_table`, optional pane scale) in memory and is the single source for three consumers: every row is drawn on the charts of its interval, rows with `show_in_table` (only single-output indicators) become market table columns, and strategies read any row. Changes apply without a restart: tables and chart catalogs read the service's current snapshot, and its change listener hands the tables' `ClosedTargets` to `Tracker.SetTargets`. Chart placement comes from the TA-Lib overlap flag and line colors from `chartPalette` in `cmd/crypto-scanner/indicators.go`; they are not configurable. Table titles are `<interval>-<type>` plus non-default parameter values (`d-rsi`, `d-rsi-21`). Do not add indicator rows, chart entries, or indicator columns in code.
- The administrator is the user whose Telegram ID is `ADMIN_TELEGRAM_ID`; `auth.Sessions` sets `auth.User.Administrator`. Administrator operations are listed in `administratorRoutes` (`router.go`), which adds `requireAdministrator` after authentication; `GET /api/v1/me` tells clients whether to offer the settings page.
- Users are added only through the administrator's chat with the Telegram bot (`telegrambot`, whose user picker supplies the Telegram identity) and listed and deleted only in the Mini App settings (`users`). A row in `app.users` is access; deleting it cascades to the user's favorites and price alerts, and the configured administrator cannot be deleted.
- Strategies are CEL expressions (`cel.dev/cel-go`) over the configured indicators and the candle fields, kept by `strategy.Service`. Each indicator output is a `double` variable named after its table title with non-identifier characters replaced by `_` (`d_rsi`, `h_macd_macdsignal`); every interval also has the built-in candle variables `<prefix>_open`, `_high`, `_low`, `_close`, `_volume`, `_quote_volume`, and `_trades` (`h_close`), which read the internal `candle` indicator module and reference no indicator row. `strategy.Compile` accepts comparisons of arithmetic (`+ - * /`, `abs`, `mod`, `min`, `max`) over variables and numbers combined with `&&`, `||`, and `!`, plus the macros `prev(x[, n])`, `percentile(x, n, p)` (nearest rank over the `n` candles before the latest), `crosses_above`/`crosses_below`, and `of("BTCUSDT", x)`, which reads `x` of another coin. The macros expand into hidden `<name>[__of_<SYMBOL>][__shift<k>]` variables of other coins and earlier closed candles; a percentile becomes a list of its operand at every shift. A coin read through `of` must be in the administrator's favorites: strategy writes check the coins an expression starts reading and record them in `app.strategy_symbols`, and the administrator's removal of such an active favorite fails with `strategy.InstrumentsInUseError` (`instrument_used_by_strategy`) until the strategies change. Both sides lock the instrument row, so the check holds under concurrency. The monitor reads such values from the snapshot of that coin and evaluates every instrument when it changes; a value read only through `of` is tracked only for that coin. Integer literals become doubles and a division or modulo by zero is an error, so the result is unknown. Keep new language features in that one compiler. The Mini App builds expressions with `@react-querybuilder/expr`; its CEL serializers in `frontend/src/features/strategy-settings/expressions.ts` must match the functions the compiler accepts. `app.strategy_indicators` references the indicators every expression reads with `ON DELETE RESTRICT`, so a used indicator cannot be deleted or cleared (`scannerindicator.ErrInUse`). `strategy.Monitor` evaluates enabled strategies over every instrument in the administrator's favorites (`ListStrategyInstruments`; other users' favorites never feed strategies) from `Tracker.Snapshot` after tracker changes (debounced) and every five minutes. Values not at the latest closed candle of their interval stay unbound, so a result that depends on them is unknown and changes nothing. A new match is stored in `app.strategy_matches` before its alert, and match writes succeed only for the evaluated strategy `revision` (bumped by every expression or enabled change) and never while its baseline is pending, so restarts, disables, and edits never produce stray or repeated alerts. Creating, re-expressing, or enabling a strategy sets `baseline_pending`; once every value it reads has been calculated (`Tracker.Snapshot` lists missing targets), the monitor replaces its matches and sends one summary, also after a restart. Indicator titles are unique because they name table columns and strategy variables; if names still collide, the older indicator keeps the name. Messages go to `ADMIN_TELEGRAM_ID` and to users with `strategy_alerts`, set on the Users settings page.
- `closedindicator` keeps closed-candle values current in the background, even with no clients, only for the indicators that enabled strategies read (`strategy.Service.Subscriptions`, supplied by `strategySource` in `app.go`), on every instrument in the administrator's favorites, or only on the coin an `of` read names; strategy changes call `Tracker.Refresh`. `Tracker.HistoryChanged` only marks changed histories and expires cached table values; tracked pairs are recalculated once per synchronization round, when `ObservableRunner` calls `Tracker.HistorySynced`. Each recalculation loads the closed history of an interval once, as deep as its deepest pair needs, and evaluates every pair over its own latest candles. Each strategy demand carries the number of points its deepest `prev` or `percentile` read needs; the tracker keeps that many latest values per output (`Output.Earlier`), loads every point with the warm-up of the latest one, and `Snapshot` reports a target as missing until it was calculated for the demanded points. Table columns read the same tracker through `Latest`, which calculates missing values on demand and caches them until the instrument's history changes, so an indicator used by no strategy costs nothing until a table shows it. Do not add per-indicator branches.
- Market tables are backend-configured. `marketTableColumns` in `cmd/crypto-scanner/tables.go` lists the static columns of the Market Scan, Top Market Cap, and Favorites tables (favorites add the alert count) with their titles, rendering kinds, sortability, and value sources, plus one `ConfiguredIndicators` slot, just before Favorite, where the administrator's indicator columns go in their configured display order. `markettable` validates the static columns at startup and builds the `table` of every analysis response, expanding the slot on every build. The frontend needs no change unless a column needs a new kind. Favorites analysis returns a row for every favorite, including instruments the analysis skipped.
- Charts are streamed over WebSocket only (snapshot plus tail updates with sequential versions). Chart logic belongs in `chart`; `httpapi` only serializes and manages the connection.
- Chart indicators are backend-configured per interval. `chart.Service` reads its catalog from a `CatalogSource` (the `scannerindicator` service), which lists what charts of an interval calculate and how clients draw them (placement, lines with theme color tokens, pane scale); clients read it from `GET /api/v1/chart/indicators?interval=`. The catalog may be empty. `scannerindicator` checks each row with `chart.ValidateIndicator` and at most `chart.MaxIndicators` rows per interval. Modules declare their outputs, and the registry rejects results that differ from them.
- `market.HistoryDepth` is the number of closed candles backfilled and kept per instrument and interval. The weekly `retention` pruner deletes older candles, and removes instruments inactive for over a week that nobody has favorited. The depth also bounds chart ranges and analysis periods (the OpenAPI chart `limit` maximum and the frontend limits mirror it). Change them together.
- Indicators come from TA-Lib through `github.com/TA-Lib/ta-lib-cgo`, which compiles the embedded C library with cgo (builds need `CGO_ENABLED=1` and a C compiler). `indicator/talib/functions_gen.go` is generated from the official `ta_func_api.xml` and checked against the wrapper signatures; one generic adapter serves every function, so never write per-indicator adapters. To upgrade TA-Lib, bump the wrapper, replace `ta_func_api.xml` with the file from the matching TA-Lib release (`ta.TALibVersion`), and run `make generate-backend`. Every arbitrary-series input (`Double Array`) gets a `source` choice parameter (`source_0`/`source_1` for two series) that picks the candle field, defaulting to close; titles name a non-default source (`h-sma-20-volume`), and an overlap function reading a non-price field is drawn in a pane. Selection parameter keys are snake_case TA-Lib option names, with `Time Period` as `period`; a single output is named after the type (`rsi`), several outputs after TA-Lib (`macd`, `macdsignal`, `macdhist`). `Registry.Normalize` returns the canonical form with defaults; client selections must go through it before they are compared, deduplicated as closed indicator targets, or stored.
- Chart builds load each selection's `Lookback` of extra closed candles before the requested range, calculate over them, and return only the requested range, so indicator values do not depend on how far the client scrolled.

## Go conventions

- Declare small interfaces at the consumer. Put every method a consumer needs into its interface; do not detect optional capabilities with runtime type assertions.
- One constructor per type. Pass required dependencies positionally and use an `Options` struct only for genuinely optional settings. Loggers are required: never fall back to `slog.Default()` or a discard logger.
- Background services implement `Run(ctx) error` and own their context. Do not store a context in a struct or create one from `context.Background()` inside a service; pass `ctx` down. Every goroutine or timer a service starts must stop before `Run` returns (use `sync.WaitGroup`; avoid `time.AfterFunc` callbacks that can fire after shutdown). Return `nil` when `ctx` is cancelled, including during startup.
- Calls from HTTP handlers into background services must never block: use non-blocking sends with a safe fallback, and make sure the fallback cannot reorder or drop committed changes.
- Use `platform/backoff` for retry delays and `platform/numeric` to validate floats; do not write new backoff loops or NaN/Inf checks. Normalize symbols with `market.NormalizeSymbol`.
- Latest-candle reads return chronological order (oldest first) through the batch `ListLatestCandles`. Keep that contract in stores and in test fakes.
- `encoding/json` matches keys case-insensitively. When decoding external payloads with keys that differ only in case (Binance sends `e`/`E`, `t`/`T`, `v`/`V`, `q`/`Q`), declare a field for every such key, even an unused one, or one value silently overwrites another.
- Logging: attach the module once with `logger.With("module", …)` or pass a consistent `"module"` value, use the `*Context` variants when a context exists, and log errors as `"error", err`.
- Wrap errors with `%w`. Reuse sentinel errors such as `market.ErrInstrumentNotFound` instead of defining parallel ones.
- Use builtin `min`/`max`, the `slices` and `maps` packages, and Go 1.23+ timer semantics; `crypto/rand.Read` does not fail.

## HTTP API

- Build error responses with the helpers in `internal/httpapi/errors.go` so generated responses carry `X-Request-ID`. Report unexpected errors with `api.internalError`, which logs the cause; never return a 500 without logging.
- Register protected operations with method-specific patterns in `protectedRoutes` (`router.go`), so unsupported methods and unknown paths are rejected before authentication.
- `httpapi.New` takes `Dependencies`, all required. Tests replace authentication through `NewWithAuthentication` in `export_test.go`.

## Storage

- Write SQL in `internal/storage/postgres/queries/` and regenerate. Prefer batch queries (`:batchone`, `unnest` joins) over per-row round trips, and `sqlc.embed` with shared row mappers such as `instrumentFromRow` over repeated field-by-field conversions. Cast computed columns so sqlc generates typed fields.
- Database integration tests run only when `CRYPTO_SCANNER_TEST_DATABASE_URL` points to a disposable empty database and `CRYPTO_SCANNER_TEST_DATABASE_RESET_OK=1` is set. They reset the schema, so never point them at the Compose database.


## Testing

- Write new tests only when the user explicitly requests them. Do not add new tests proactively for features, fixes, refactors, or code review findings. Update existing tests as needed to reflect functionality changes; no separate user request is required. Running existing tests is allowed.
- When explicitly requested, add tests only when they verify meaningful behavior, transformations, validation, branching, edge cases, or regression-prone contracts. Do not add a test merely because a source file was added or changed.
- Do not test static configuration or constants by duplicating their values in assertions. Exercise configuration indirectly through behavioral tests when doing so protects real behavior.

## OpenAPI generation

- `internal/httpapi/openapi/openapi.yaml` is the authoritative HTTP API contract shared by the backend and frontend.
- `internal/httpapi/openapi.gen.go` is generated by `oapi-codegen`. Never edit it manually.
- Generator configuration lives in `internal/httpapi/openapi/oapi-codegen.yaml`; the pinned tool declaration lives in `tools.go`.
- After changing the contract or generator configuration, run `make generate-backend` from the repository root.
- When a contract change affects frontend consumers, run `make generate` so both backend bindings and the frontend client are regenerated from the same contract.
- After changing sqlc queries or configuration, run `make generate-sqlc` from the repository root. SQL bindings are committed and must not be edited manually.
- Commit the contract and all resulting generated files together. CI regenerates them and rejects drift.
