# Backend

## Architecture

Composition happens only in `cmd/crypto-scanner/app.go`: it builds every dependency, the HTTP handler, and the list of background services that `lifecycle.go` runs (HTTP first, then the services; the first to stop stops the rest). Add a new background service to that list instead of starting goroutines elsewhere.

Packages and dependency direction (domain never imports adapters):

- Domain: `market` (instruments, candles, intervals, `NormalizeSymbol`), `market/kline` and `market/trade` (exchange-neutral live feeds), `market/live` (demand-driven live candle subscriptions), `market/gridlimits` (inputs of the Binance spot grid bot price range limits and tick size, from which clients compute the lowest lower and highest upper price: only for active instruments; the average price cached per symbol for a few seconds, the price filters cached per symbol for 24 hours after a client asks; no background refresh), `market/marketsync` (REST history sync and scheduler; `ObservableStore` reports committed candle changes and `ObservableRunner` the end of each synchronization round), `indicator` (registry of self-describing indicator modules plus `Registry.CalculateCandles`), `chart` (closed chart ranges and `LiveSession`, which merges live candles with history), `closedindicator` (background indicators on closed candles), `analysis` (criteria pipeline), `markettable` (backend-defined market tables), `scannerindicator` (administrator-configured indicators), `strategy` (administrator strategies over those indicators and their Telegram alerts), `users` (administrator user management), `favorites`, `alerts`, `marketcap`, `auth`.
- Adapters: `indicator/talib` (every TA-Lib function through one generic adapter), `indicator/pivot` (pivots and the RSI divergence TA-Lib lacks), `exchange/binance` (REST client and one generic WebSocket `streamPool` for kline and trade streams), `coingecko`, `storage/postgres` (one `Store`, split into `store_*.go` by aggregate), `httpapi` (transport only), `telegrambot`, `auth/telegram` (init-data verification, no `net/http`).
- Authentication: `auth.Sessions` exchanges Telegram init data (at most `TELEGRAM_INIT_DATA_MAX_AGE` old, checked by `auth/telegram`) for an opaque random token through `POST /api/v1/auth/session`. Only the token's SHA-256 is stored in `app.sessions`, which cascades from `app.users`, so deleting a user revokes their sessions. Every other operation and the live candle WebSocket's `authenticate` message use the token (`Authorization: Bearer`); it expires after `SESSION_IDLE_TTL` without use and after `SESSION_ABSOLUTE_TTL`, and the WebSocket rechecks it every minute. Never accept init data elsewhere. API tokens (`cst_` prefix, `/api/v1/admin/api-tokens`) are the non-Telegram credential for clients such as the CLI: `auth.Sessions.Authenticate` checks them against `app.api_tokens` (SHA-256 only, cascading from `app.users`) with their owner's rights, never expires them, and records `last_used_at` at most once a minute (a failed write is logged at WARN and never refuses the token); deleting a token revokes it. API tokens keep every right of their owner except managing API tokens and starting history loads: those handlers refuse them with 403 `session_required` (`auth.User.APIToken`), and the CLI client is generated without those operations.
- CLI: `cmd/scanner` talks to the API only through `internal/apiclient`, generated by oapi-codegen from `openapi.yaml` (`oapi-codegen-client.yaml`, part of `make generate-backend`). It must stay free of cgo and of database, indicator, and other server packages, so `go install` works anywhere; `deps_test.go` checks this. Build it separately with `make install-cli`; the backend Dockerfile builds only `cmd/crypto-scanner` and `cmd/migrate`, never `cmd/...`. Commands, flags, argument checks, help, and shell completion come from `github.com/spf13/cobra`; do not hand-write dispatch, usage text, or completion scripts. Cobra's own error printing is off: `run` prints every error once on stderr (`cliError` in `errors.go`), as `scanner: …` text, or with `--json` in the API error shape `{"error":{"code","message","details"},"request_id"}`; API errors keep their code, details, and request ID, and local failures get fixed codes (`usage` for flag and argument errors, `no_profile`, `config`, `unreachable`, `unexpected_response`, `invalid_expression`, …). With `--json`, stdout carries only the result, also for commands whose API response has no body. Any error exits with 1; an interrupted command exits quietly. Generated `*WithResponse` calls decode responses; do not decode bodies by hand. Never print the token. `scanner strategies` and `scanner signals` are separate command groups over the same saved strategies (`kind` in `signals.go`): each lists, edits, and deletes only its own and refuses the other's IDs, and nothing changes the kind or the direction of a saved one: `Service.Update` refuses a change of `Signal` or `Direction`. `create --direction` takes `long` or `short` in `scanner strategies` and also `sideways` in `scanner signals` (`kind.directions`); `update` has no `--direction`. `scanner strategies backtest` and `scanner signals backtest` backtest unsaved rules with the flags of `create`. Every backtest command first takes a non-blocking file lock (`lockBacktest`, `github.com/gofrs/flock`, `backtest.lock` beside the configuration file), so one backtest runs per machine and another fails at once.
- Shared helpers: `platform/backoff` (retry delays, `Sleep`), `platform/numeric` (`Finite`, `ParseFinite`), `platform/logging`, `platform/config`.
- Every WARN and ERROR record of the process logger is forwarded to `opsnotify`, which sends it to the administrator through the Telegram bot (repeats of the same level, module, and message become one summary per hour). Log at WARN or above only what the administrator should read.

Product constraints:

- Indicators are configured by the administrator, not in code. `scannerindicator` keeps the rows of `app.scanner_indicators` (indicator type, canonical parameters, interval, `show_in_table`, `show_in_chart`, optional pane scale) in memory and is the single source for three consumers: rows with `show_in_chart` are drawn on the charts of their interval, rows with `show_in_table` (only single-output indicators) become market table columns, and strategies read any row. Changes apply without a restart: tables and chart catalogs read the service's current snapshot, and its change listener hands the table columns' targets (`TableTargets`) to `Tracker.SetTargets`. Chart placement comes from the module's overlay flag and line colors from `chartPalette` in `cmd/crypto-scanner/indicators.go`; they are not configurable. Table titles are `<interval>-<type>` plus parameter values: values other than named choices in order up to the last non-default one, so each keeps its position (`d-rsi`, `d-rsi-21`, `h-bbands-20-2.5`, `h-bbands-20-2-2.5`), and named choices such as the source once one differs. Do not add indicator rows, chart entries, or indicator columns in code.
- The administrator is the user whose Telegram ID is `ADMIN_TELEGRAM_ID`; `auth.Sessions` sets `auth.User.Administrator`. Administrator operations are listed in `administratorRoutes` (`router.go`), which adds `requireAdministrator` after authentication; `GET /api/v1/me` tells clients whether to offer the settings page.
- Users are added only through the administrator's chat with the Telegram bot (`telegrambot`, whose user picker supplies the Telegram identity) and listed and deleted only in the Mini App settings (`users`). A row in `app.users` is access; deleting it cascades to the user's favorites and price alerts, and the configured administrator cannot be deleted.
- Strategies are CEL expressions (`cel.dev/cel-go`) over the configured indicators and the candle fields, kept by `strategy.Service`: an entry rule, an optional exit rule that also reads the position variables of the open trade (`PositionVariables`: `entry_price`, `pnl`, `bars_held`, no target, latest candle only), and optional take profit and stop loss price expressions (`CompilePrice`: arithmetic without comparisons, reading the evaluated coin). Every expression goes through the one compiler (`RuleKind` picks entry, exit, or price); a strategy trades on the finest interval any of them reads (`Entry.Interval`), and everything that reads indicators or coins (`strategy_indicators`, `strategy_symbols`, subscriptions) covers all of them. A strategy with any exit (`Entry.Exits`) holds one buy per trade; one without buys at every entry signal and never sells. Every strategy has a `Direction` (`app.strategies.direction`): a trading strategy trades `long` or `short`, and one with `Signal` (`app.strategies.signal`) is a signal instead, expecting a `long`, `short`, or `sideways` move: it has no exits (checked by `Service.entry` and table constraints) but may have a market cap range like a strategy, and it alone has a `TargetRatio` (2, 3, 4, or 5 stops) and a `Window` (3, 6, 12, or 24 candles), which only its backtest reads (`app.strategies.target_ratio` and `window_candles`, required for signals and NULL for trading strategies by a table constraint), and `Entry.step` turns its entry signals within that range into `TradeSignal` events that buy nothing and alert with the expected move. A short strategy always has a take profit and a stop loss (also a table constraint), so it holds one position per trade: `Entry.step` mirrors its levels (take profit below and stop loss above the close, `levelsAround`; the stop loss reached by the high, the take profit by the low, `levelExit`), and its returns and `pnl` come from `Direction.gross` (`1 − exit/entry`); alerts say short and cover. The language, the limits, and the variable names are described in `docs/strategy-language.md`; update it with every language or naming change. Every indicator output is a `double` variable; the built-in candle variables read the internal `candle` indicator module and reference no indicator row. The macros expand into hidden `<name>[__of_<SYMBOL>][__shift<k>]` variables of other coins and earlier closed candles; a percentile becomes a list of its operand at every shift. Strategy writes check that the coins an expression starts reading through `of` are in the administrator's favorites and record them in `app.strategy_symbols`, and the administrator's removal of such an active favorite fails with `strategy.InstrumentsInUseError` (`instrument_used_by_strategy`) until the strategies change. Both sides lock the instrument row, so the check holds under concurrency. The monitor reads such values from the snapshot of that coin and evaluates every instrument when it changes; a value read only through `of` is tracked only for that coin. Integer literals become doubles and a division or modulo by zero is an error, so the result is unknown. Keep new language features in that one compiler. `Service.Validate` resolves variables of indicators that are not configured into `Validation.Missing` (`missing.go`): it tries every reading of the name as interval, type, and parameter values and keeps the indicator whose title spells the name back, only when exactly one does; the Mini App import offers to add them through `POST /api/v1/admin/scanner-indicator-batches` before importing the expression. The Mini App builds expressions with `@react-querybuilder/expr`; its CEL serializers in `frontend/src/features/strategy-settings/expressions.ts` must match the functions the compiler accepts. `app.strategy_indicators` references the indicators every expression reads with `ON DELETE RESTRICT`, so a used indicator cannot be deleted or cleared (`scannerindicator.ErrInUse`). Clearing (`Service.DeleteUnused`, the `DeleteUnusedScannerIndicators` query, the one place of the rule) removes only indicators that no strategy reads and with neither `show_in_table` nor `show_in_chart`. Trading is one state machine, `Entry.step` (`position.go`), shared by the monitor and the backtest so they never diverge: per strategy and instrument a `TradeState` (last processed candle, entry value, buys, fills, coins bought, first fill) advances once per closed candle of the strategy's interval; an entry signal is the entry turning from false to true and buys (opens a trade, fixing its take profit and stop loss from the price expressions at the signal's close and skipping a signal whose levels are not on their sides of the close, or adds a buy for a strategy without exits; a strategy with exits skips signals during a trade), buys fill at the next processed candle's open with one quote unit each, and the first fill starts the trade (`bars_held`). A filled trade sells at its stop loss or take profit on the candle reaching them (high and low; at the open when it opens past one; the stop loss first when it reaches both), then an exit signal (exit rule true) sells every buy at the next open; any sell counts the entry as false on its candle, and exits win over entry. `TradeState` keeps the fixed levels, and sell events carry their reason. A candle waits, unprocessed, until every expression it needs is known: the exit rule during a trade, and the entry and the levels of a trade it opens unless the trade sells. `strategy.Service.Backtest` replays it for a saved strategy on any active coin, one coin per request to keep the server responsive, over its stored history with `closedindicator.Calculate`, reading `of` only among the administrator's favorites, over the candles opening within an optional `from`–`to` period (older candles still warm indicators up); exit rule sells fill at the next open and level sells at their price, `BacktestFee` applies on both sides, and a trade the history ends before selling stays open, valued at the last close (in net profit and equity, not in the closed-trade statistics). Each trade reports its fills with the values the entry rule read at their signals (`Expression.Values`, named as the source writes them, reads inside percentile windows left out), its levels, its exit reason, and the values the exit rule read at its signal; the drawdown is measured at every evaluated candle's close with the open trade valued there, and the statistics count exits by reason and the average candles held. Baselines over the evaluated period of a long strategy: buy and hold, and DCA (one unit at every candle's open, valued at the last close); a short strategy has none, and its backtest (`netReturn` by direction) ignores funding, leverage, and liquidation. A signal's backtest has no trades or baselines; `Backtest.Signal` (`signalReport`) judges the close of each signal candle and of every evaluated candle by a stop and a target over the signal's `Window` candles (`evaluateSignal`): the stop lies the sample standard deviation of the `signalVolatilityCandles` (100) one-candle returns up to the candle times √`Window` against the expected move, the target `TargetRatio` stops in its direction (sideways: both sides, no stop); long and short succeed when the target comes before the stop (`directionalOutcome`: a candle reaching both fails unless its open already is at one), sideways when neither target is touched, and the move to target runs until the stop candle's open or the window's end. A candle without 101 consecutive closes before it or the whole consecutive window after it has no evaluation. Counted signals are at least a window apart; the report gives the evaluated, counted, and successful signals and their median move beside the same over every evaluated candle, and lists every signal with the entry values and its evaluation; outcomes may read stored candles after `to`. `Service.BacktestDraft` replays an unsaved strategy or signal the same way (`POST /api/v1/admin/strategy-backtests`), checked and compiled by `Service.trading`, which a save runs too, without the name, message, and market cap checks, and refused, like a save, when a coin it reads through `of` is not an active favorite of the administrator; nothing is stored. The draft commands of the CLI validate the rules first (`prepareStrategyRules`, never adding indicators), like `create`. At most `maxBacktests` (2) backtests, saved or not, run at once; another fails at once with `ErrBacktestBusy` (429 `backtest_busy`). `strategy.Monitor` evaluates enabled strategies over every instrument in the administrator's favorites (`ListStrategyInstruments`; other users' favorites never feed strategies) from `Tracker.Snapshot` after tracker changes (debounced) and every five minutes. Values not at the latest closed candle of their interval stay unbound, so a result that depends on them is unknown and changes nothing. Each processed candle's `TradeState` is stored in `app.strategy_states` before its buy or sell alert; state writes succeed only for a later candle than the stored one, for the evaluated strategy `revision` (bumped by every change of a rule or price expression and by enabled changes), and never while its baseline is pending, so restarts, disables, and edits never produce stray or repeated alerts. The monitor processes only the latest closed candle, so candles that close while the backend is down are not replayed. Creating, changing how a strategy trades, or enabling it sets `baseline_pending`; once every value it reads has been calculated (`Tracker.Snapshot` lists missing targets), the monitor replaces its states with the current entry values and no trades, and sends one summary, also after a restart. Indicator titles are unique because they name table columns and strategy variables; if names still collide, the older indicator keeps the name. Messages go to `ADMIN_TELEGRAM_ID` and to users with `strategy_alerts`, set on the Users settings page.
- `closedindicator` keeps closed-candle values current in the background, even with no clients, only for the indicators that enabled strategies read (`strategy.Service.Subscriptions`, the tracker's one `Source`), on every instrument in the administrator's favorites, or only on the coin an `of` read names; strategy changes call `Tracker.Refresh`. `Tracker.HistoryChanged` only marks changed histories and expires cached table values; tracked pairs are recalculated once per synchronization round, when `ObservableRunner` calls `Tracker.HistorySynced`. Each recalculation loads the closed history of an interval once, as deep as its deepest pair needs, and evaluates every pair over its own latest candles. Each strategy demand carries the number of points its deepest `prev` or `percentile` read needs; the tracker keeps that many latest values per output (`Output.Earlier`), gives every point the `chart.Window` warm-up, and `Snapshot` reports a target as missing until it was calculated for the demanded points. Table columns read the same tracker through `Latest`, which calculates missing values on demand and caches them until the instrument's history changes, so an indicator used by no strategy costs nothing until a table shows it. Do not add per-indicator branches.
- Market tables are backend-configured. `marketTableColumns` in `cmd/crypto-scanner/tables.go` lists the static columns of the Market Scan, Top Market Cap, and Favorites tables (favorites add the alert count) with their titles, rendering kinds, sortability, and value sources, plus one `ConfiguredIndicators` slot, just before Favorite, where the administrator's indicator columns go in their configured display order. `markettable` validates the static columns at startup and builds the `table` of every analysis response, expanding the slot on every build. The frontend needs no change unless a column needs a new kind. `markettable.Service` assembles every table, the favorites table included (`Service.Favorites` takes the favorites the handler listed); `favorites` only lists, adds, and removes. Favorites analysis returns a row for every favorite, including instruments the analysis skipped.
- Charts are streamed over WebSocket only (snapshot plus tail updates with sequential versions). Chart logic belongs in `chart`; `httpapi` only serializes and manages the connection.
- Chart indicators are backend-configured per interval. `chart.Service` reads its catalog from a `CatalogSource` (the `scannerindicator` service), which lists what charts of an interval calculate and how clients draw them (placement, lines with theme color tokens, pane scale, and pane key: pane indicators of one type reading fields of the same units share a pane, while types with a histogram output, such as MACD, get one pane each); clients read it from `GET /api/v1/chart/indicators?interval=`. The catalog may be empty. `scannerindicator` checks each row with `chart.ValidateIndicator` and at most `chart.MaxIndicators` rows per interval, whether or not charts draw them. Modules declare their outputs, and the registry rejects results that differ from them.
- Two depths bound candle history. `market.SyncDepth` (2,000) is what synchronization backfills and keeps complete per instrument and interval; it bounds chart ranges (`chart.MaxRange`), the `chart.Window` cap, TA-Lib integer parameters, analysis periods, and the history strategies may read (`Service.compile`), so everything live works on synchronized history alone (the OpenAPI chart `limit` maximum and the frontend limits mirror it; change them together). `market.RetentionDepth` (20,000) is what the weekly `retention` pruner keeps, and what backtests read; the pruner also removes instruments inactive for over a week that nobody has favorited. Candles beyond `SyncDepth` come from synchronized candles accumulating and from `marketsync.HistoryLoader`, a background service that runs one job at a time, started only by the administrator from the Mini App (`POST /api/v1/admin/candle-history-loads` returns 202 at once, 409 `history_load_running` while a job runs, and 403 `session_required` to a request authenticated with an API token, which `auth.User.APIToken` marks; `GET` shows the current or last job, kept in memory only). It extends histories backwards through `Synchronizer.LoadHistory` (notifying committed changes only while filling a history shorter than `SyncDepth`, then ending that load's tracker round even after a partial failure; deeper pages use the plain store and notify nothing) at the history repair rate limit until the requested depth (at most `RetentionDepth`) or the exchange's oldest candle, recorded as coverage like the exhaustion `Sync` finds. An empty history fails `LoadHistory` with `ErrHistoryNotReady`, since initial backfill belongs to `Sync`; the job skips that pair as a `not_ready` item and goes on with the others. Jobs report `history_changed` even if a later page fails, so clients can tell that a failed load still stored candles. Backtests never call the exchange: they read stored candles within `backtestTimeout` (below the server's read and write timeouts) and fail with 503 `backtest_too_heavy` past it. The server refuses API tokens there, and the CLI client is generated without that operation (`exclude-operation-ids` in `oapi-codegen-client.yaml`), so agents and the `scanner` CLI cannot start history loads or manage API tokens. `Sync` summarizes only the latest `SyncDepth` candles, so it never refetches, repairs, or counts deeper rows.
- Besides TA-Lib, `indicator/pivot` provides the swing indicators TA-Lib lacks, as TradingView calculates them: `pivot` (latest and previous confirmed pivot highs and lows) and `divergence` (its RSI Divergence Indicator, regular and hidden), which gets the TA-Lib RSI module in `indicatorModules` so its RSI matches the configured one. They are ordinary registry modules that every consumer reads like TA-Lib functions; add another only for a calculation TA-Lib cannot do. Pivots count only within the 500 candles ending at each value, with the candles before them, so a value never depends on how much history a caller passes (charts pass more than the tracker); their lookback makes `chart.Window` load that window, and a series keeps only its last unbroken run. Parameter numbers and input series are checked by the shared `indicator.ParseNumber` and `indicator.ReadInputs`.
- Indicators come from TA-Lib through `github.com/TA-Lib/ta-lib-cgo`, which compiles the embedded C library with cgo (builds need `CGO_ENABLED=1` and a C compiler). `indicator/talib/functions_gen.go` is generated from the official `ta_func_api.xml` and checked against the wrapper signatures; one generic adapter serves every function, so never write per-indicator adapters. To upgrade TA-Lib, bump the wrapper, replace `ta_func_api.xml` with the file from the matching TA-Lib release (`ta.TALibVersion`), and run `make generate-backend`. Every arbitrary-series input (`Double Array`) gets a `source` choice parameter (`source_0`/`source_1` for two series) that picks the candle field, defaulting to close; titles name a non-default source (`h-sma-20-volume`), and an overlap function reading a non-price field is drawn in a pane. Selection parameter keys are snake_case TA-Lib option names, with `Time Period` as `period`; a single output is named after the type (`rsi`), several outputs after TA-Lib (`macd`, `macdsignal`, `macdhist`). `Registry.Normalize` returns the canonical form with defaults; client selections must go through it before they are compared, deduplicated as closed indicator targets, or stored.
- `chart.Window` is the one warm-up policy of charts, the closed indicator tracker, and backtests: the lookback times a settle factor, capped at half of `market.SyncDepth`, so recursive indicators (EMA, RSI, ADX, MACD, …) settle past their seed. Chart builds load the largest window of the selection before the requested range, calculate each indicator over its own window only, and return only the requested range, so indicator values do not depend on how far the client scrolled, on the other selected indicators, or on the points a strategy keeps. Live charts run in `chart.LiveStream` (one goroutine per subscribed key, events coalesced into one frame for the strongest trigger) inside a `chart.LiveGroup` that the WebSocket handler waits for before returning.

## Go conventions

- Declare small interfaces at the consumer. Put every method a consumer needs into its interface; do not detect optional capabilities with runtime type assertions.
- One constructor per type. Pass required dependencies positionally and use an `Options` struct only for genuinely optional settings. Loggers are required: never fall back to `slog.Default()` or a discard logger.
- Background services implement `Run(ctx) error` and own their context. Do not store a context in a struct or create one from `context.Background()` inside a service; pass `ctx` down. Every goroutine or timer a service starts must stop before `Run` returns (use `sync.WaitGroup`; avoid `time.AfterFunc` callbacks that can fire after shutdown). Return `nil` when `ctx` is cancelled, including during startup.
- Calls from HTTP handlers into background services must never block: use non-blocking sends with a safe fallback, and make sure the fallback cannot reorder or drop committed changes.
- Use `platform/backoff` for retry delays and `platform/numeric` to validate floats; do not write new backoff loops or NaN/Inf checks. Normalize symbols with `market.NormalizeSymbol`.
- Latest-candle reads return chronological order (oldest first) through the batch `ListLatestCandles`. Keep that contract in stores and in test fakes.
- `encoding/json` matches keys case-insensitively. When decoding external payloads with keys that differ only in case (Binance sends `e`/`E`, `t`/`T`, `v`/`V`, `q`/`Q`), declare a field for every such key, even an unused one, or one value silently overwrites another.
- Logging: attach the module once with `logger.With("module", …)` or pass a consistent `"module"` value, use the `*Context` variants when a context exists, and log errors as `"error", err`.
- Wrap errors with `%w`. Reuse sentinel errors such as `market.ErrInstrumentNotFound` instead of defining parallel ones.
- Use builtin `min`/`max`, the `slices` and `maps` packages, and Go 1.23+ timer semantics; `crypto/rand.Read` does not fail.

## HTTP API

- Build error responses with the helpers in `internal/httpapi/errors.go` so generated responses carry `X-Request-ID`. Report unexpected errors with `api.internalError`, which logs the cause; never return a 500 without logging.
- Requests the OpenAPI validator rejects get `invalid_argument` naming the parameter or body field and the reason (`requestErrorMessage` in `router.go`), never kin-openapi's schema and value dumps.
- Register protected operations with method-specific patterns in `protectedRoutes` (`router.go`), so unsupported methods and unknown paths are rejected before authentication.
- `httpapi.New` takes `Dependencies`, all required. Tests replace authentication through `NewWithAuthentication` in `export_test.go`.

## Storage

- Write SQL in `internal/storage/postgres/queries/` and regenerate. Prefer batch queries (`:batchone`, `unnest` joins) over per-row round trips, and `sqlc.embed` with shared row mappers such as `instrumentFromRow` over repeated field-by-field conversions. Cast computed columns so sqlc generates typed fields.
- Database integration tests run only when `CRYPTO_SCANNER_TEST_DATABASE_URL` points to a disposable empty database and `CRYPTO_SCANNER_TEST_DATABASE_RESET_OK=1` is set. They reset the schema, so never point them at the Compose database.


## Testing

- Write tests only where they are really needed: important logic whose breakage would be costly, such as calculations, transformations, validation, branching, edge cases, or regression-prone contracts. Keep them to a minimum. Never write tests for their own sake, to reach a count, or merely because a source file was added or changed, and never write tests that restate configuration, constants, or declarations: a test that repeats what the config says is an anti-pattern.
- Update existing tests as needed to reflect functionality changes. Running existing tests is allowed.
- Do not test static configuration or constants by duplicating their values in assertions. Exercise configuration indirectly through behavioral tests when doing so protects real behavior.

## OpenAPI generation

- `internal/httpapi/openapi/openapi.yaml` is the authoritative HTTP API contract shared by the backend and frontend.
- `internal/httpapi/openapi.gen.go` is generated by `oapi-codegen`. Never edit it manually.
- Generator configuration lives in `internal/httpapi/openapi/oapi-codegen.yaml` (server) and `oapi-codegen-client.yaml` (the CLI client in `internal/apiclient`); the pinned tool declaration lives in `tools.go`.
- After changing the contract or generator configuration, run `make generate-backend` from the repository root.
- When a contract change affects frontend consumers, run `make generate` so both backend bindings and the frontend client are regenerated from the same contract.
- After changing sqlc queries or configuration, run `make generate-sqlc` from the repository root. SQL bindings are committed and must not be edited manually.
- Commit the contract and all resulting generated files together. CI regenerates them and rejects drift.
